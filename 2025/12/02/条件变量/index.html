条件变量

条件变量的定义及概念

  • 条件变量是利用线程间共享的变量（公共资源）进行同步的一种机制，是在多线程程序中用来实现等待–>唤醒逻辑常用的方法，线程可以使用条件变量来等待某个条件为真，注意理解并不是等待条件变量为真。
  • 当条件不满足时，线程将自己放入等待队列，同时释放自己拥有的互斥锁

  • 条件变量（Condition Variable）的一般用法是：线程 A 等待某个条件并挂起，直到线程 B 设置了这个条件，并通知条件变量，然后线程 A 被唤醒。经典的「生产者-消费者」问题就可以用条件变量来解决。

可以避免不必要的竞争

如直接使用mutex，除了生产者、消费者之间要竞争互斥量以外，消费者之间也需要竞争互斥量，但如果汇聚（链表）中没有数据，消费者之间竞争互斥锁是无意义的。有了条件变量机制以后，只有生产者完成生产，才会引起消费者之间的竞争。提高了程序效率。

简而言之：当汇聚中没有任何数据时，消费者不必要一直竞争锁而造成资源浪费。如果生产者生产出数据放入汇聚中，即可唤醒消费者引起竞争

为什么采用while而不采用if

原因 1：多消费者竞争 假设有两个消费者线程等待。生产者生产了一个数据并唤醒了所有等待线程（或先后唤醒）。消费者 1 率先抢到锁并消费了数据。当消费者 2 随后抢到锁并从 wait 返回时，此时队列再次为空。如果使用 if，消费者 2 会直接向下执行，导致访问空指针或越界错误；使用 while 则会再次检查条件，发现为空后重新进入挂起状态。

原因 2：防御虚假唤醒 (Spurious Wakeup) 在某些操作系统底层实现中，线程可能会在没有收到 signal/notify 的情况下被意外唤醒。使用 while 循环可以强制线程在醒来后重新验证条件，确保逻辑绝对安全。

C++条件变量使用

等待函数

condition_variable有三个等待函数：wait()、wait_for() 和 wait_util()。这三个函数需要与互斥锁一起使用，以互斥的方式访问共享资源，并阻塞线程，等待通知。

  • wait()

    如果条件变量当前不满足，线程将被阻塞，同时释放锁，使得其他线程可以继续执行。

    第二个参数是一个谓词，可以传入lambda表达式

  • wait_for()

​ 可以设置超时时间：

​ 如果条件变量在指定的超时时间内变为满足，线程将被唤醒，并且 wait_for() 返回 cv_status::no_timeout。

​ 如果超时时间到期且仍未收到唤醒通知，wait_for() 返回 cv_status::timeout，线程继续执行。

  • wait_until()

    wait_until() 接受一个绝对时间点作为参数。

    线程将等待直到指定的绝对时间点，如果在该时间点之前条件变量满足，它将返回并继续执行。

    如果到达指定时间点仍未收到唤醒通知，wait_until 返回 cv_status::timeout，线程继续执行。

通知函数

通知函数有 notify_one() 和 notify_all()。类似系统调用接口中的pthread_cond_signal 和 pthread_cond_broadcast

  • notify_one()

​ notify_one() 用于唤醒等待在条件变量上的单个线程。

  • notify_all()

    notify_all() 用于唤醒等待在条件变量上的所有线程。

为什么要加锁之后再使用条件变量，为什么推荐解锁后再进行唤醒

场景：等待某个 “状态” 发生改变（比如 count > 0 或 is_ready == true）。

  • 条件变量 (cond)：用来“睡觉”和“唤醒”。
  • 互斥锁 (lock)：必须绑定使用，用来保护那个“状态”。

1. 等待端 (Wait) 的顺序 —— 【必须在锁里】

绝对规则：pthread_cond_wait 必须放在 lock 和 unlock 之间，且必须配合 while 循环。

  • 为什么要先加锁？
    • 因为 ready 变量是共享的，判断 while(ready == false) 本身就需要保护。
    • pthread_cond_wait 的内部逻辑是：原子地（Unlock mutex -> Sleep -> … -> Wakeup -> Lock mutex）。如果不加锁，无法完成这一系列操作

2. 发送端 (Signal) 的顺序

两种写法都可以，但推荐先 Unlock 再 Signal。

写法 A (推荐)：先解锁，再通知

  • 优点：效率高。唤醒等待线程时，它不用和当前线程争抢锁。

写法 B (也可以)：在锁里通知

  • 缺点：等待线程醒来后发现锁还在你手里，只能立刻再次休眠等待锁释放（性能稍差）。
  1. 调用notify_one()先唤醒等待的消费者线程
  2. 消费者线程尝试抢锁，但锁还没被释放，导致抢锁失败
  3. 生产者调用unlock
  4. 消费者再次抢锁

消费者被毫无意义的唤醒了一次，这种**无效的上下文切换 (Context Switch)**极其消耗 CPU 资源，在高并发场景下会导致严重的性能衰退。
